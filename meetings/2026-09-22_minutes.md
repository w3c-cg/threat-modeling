### Linking Threat Models to Specifications

* elf Pavlik: I would like concrete guidance on linking threats and responses to normative requirements, Security Considerations, Privacy Considerations, and tests. Solid already uses identifiers for individual requirements and links tests to them. We could reuse those identifiers and give considerations stable anchors too. * elf Pavlik: Plain links are a useful starting point, but I would also like a lightweight, optional structure that identifies the relationships. I am also interested in optional security tests beyond isolated conformance tests; that is an idea I have not tried yet.

* Joe Andrieu: ReSpec Threats supports links in descriptions. Preserving structured data in published specifications for later analysis is a broader question. I support exploring it, but I do not have a recommendation on the format. The current design deliberately gives threat modelers flexibility.

* Simone Onofri: In the models I am working on, links connect diagram elements to specification sections and responses to the relevant requirements. They also help us check what the model covers. The guide should allow different ways to do this.

### Response Terminology and Examples

* elf Pavlik: Should we use “response” as the general term and “mitigation” for reduction, rather than treating them as synonyms?

* Joe Andrieu: Yes. “Mitigation” is used ambiguously in the field. The eliminate, reduce, transfer, accept terminology helps us avoid that ambiguity.

* Simone Onofri: The mnemonic describes what we do about a threat. We can consider elimination, reduction, and transfer, and then account for what remains. Threats and responses have a many-to-many relationship. Each threat should have at least one response, and residual risk remains to be accepted unless the threat is eliminated.

* elf Pavlik: We also need examples showing whether a link belongs on the threat or its response, and how one response can connect to several requirements or considerations.

* Joe Andrieu: Either can link to relevant parts of the specification. The point is to connect the model to the specification. Our guide examples do not yet demonstrate the level of linking we want.

* Simone Onofri: The Vibration API work provides an earlier example, although it predates the guide's terminology. We should add specification-specific examples to help readers whose main work is specification development rather than security.

* elf Pavlik: A small collection of maintained examples could show these practices without forcing every detail into the abstract Threat Model for the Web.

* Joe Andrieu: Better examples, consistent response identifiers, and links back to specifications would be useful things to work on before TPAC.

### WebMCP Deployment Scenarios and Diagram Gaps

* Simone Onofri: The current model distinguishes an agent operated on the user's side from an agent provided by the page. The agent's context and the location of its control change the story we need to model. I still need to add the agent-context data store and the embedded-iframe case.

* Joe Andrieu: The browser-integrated diagram is missing the pending tool executions map. Is that intentional, or a diagram omission?

* Simone Onofri: That is missing from the first diagram. Thank you for spotting it.

* Joe Andrieu: We should distinguish an agent built into the browser, a browser extension, and an external agent driving a browser. They have different interfaces and permission boundaries. Where is the user involved when the agent needs additional authority?

* elf Pavlik: Are extensions a separate scenario? Does the model also account for multiple agents operating at once?

* Simone Onofri: I see user-side and page-provided agents as two families with different deployment variants. An external agent may get approval through its terminal, while another uses a browser interface. We may need separate diagrams to show those flows.

* Joe Andrieu: Co-browsing implies some integration between the user's and agent's browsing. Independent browsing with a separate communication channel is a different case. The approval flow needs to be visible so that we can examine where it could fail.

* Joe Andrieu: The model should also show how a browsing session is associated with the agent interaction and where user presence and authorization are checked. Web security often treats a user action differently from a script action, and an agent can act through the user's session without the user being present for each step.

* Simone Onofri: WebMCP does not itself identify the user. The page can distinguish an `executeTool` invocation from an ordinary form submission, but the model still needs to account for the surrounding agent and browser session.

* Joe Andrieu: After looking at the WebMCP material, I need to correct my earlier mental model. I had assumed a remote MCP endpoint. Here, the page exposes JavaScript functionality for the agent to invoke.

* Simone Onofri: Yes, the effect is on the web page. WebMCP provides a structured way for agents to use website functionality.

### Cross-Origin Tools and Agent Authority

* Joe Andrieu: Cross-origin tools need to appear in the diagrams. They raise questions about which third-party services are trusted and what those services can do.

* Simone Onofri: My interpretation is that the mechanism lets another origin invoke selected tools without access to the page's full JavaScript context. We should check that interpretation with the WebMCP editors.

* elf Pavlik: Are we comparing this with CORS or CSP? CORS is controlled by the server hosting the resource.

* Joe Andrieu: CSP is closer to the comparison I intended. I am concerned about adding a separate control layer that people could misunderstand or misconfigure. An agent with broader extension permissions may still use other page interfaces even when the WebMCP path is constrained.

* Simone Onofri: Many of these problems also exist in agentic browsing without WebMCP. The question is whether WebMCP can help address some of them.

* Joe Andrieu: I want to express permission at the level of user intent: for example, browse a shop as me but do not purchase. I am not sure existing permission semantics express that distinction or make its consequences understandable to users.

* elf Pavlik: We could invite people working on Web Extensions to a future session through the public mailing list, so we can discuss the extension-agent case with them.
